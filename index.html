Safety Architecture Review

Medical Evidence Q&A Assistant

This page reviews a medical evidence question-answering assistant from the safety boundary inward. The available project description is modest and that is useful: it claims trusted-source retrieval from medical PDFs, guidelines, and PubMed-style references; PDF extraction, cleanup, chunking, embeddings, Qdrant indexing, reranking, constrained answer generation, explicit refusals, and FastAPI exposure. The review below stays inside those stated mechanics rather than treating the system like an already-audited clinical product.

Primary Position Education-focused assistant, not a diagnosis engine and not an open-ended medical chatbot.
Safety Core Evidence retrieval and refusal logic carry more safety weight than the generation model itself.
Failure Mode To Avoid Clean prose that outruns retrieved evidence or quietly substitutes model prior for source support.
Review Basis Architecture-level claims from the project README, interpreted conservatively and without invented runtime metrics.

Scope Of Review

This is a design review of a stated system pattern. It is not a certification, not a clinical efficacy claim, and not evidence that the FastAPI surface or refusal policy has been independently tested in production.

Why The Order Matters

  • Risk boundary first, because the rest of the stack is only acceptable inside a narrow mandate.
  • Retrieval second, because source control is the main defense against model improvisation.
  • Answer assembly third, because citation behavior is where grounded systems often drift.
  • Refusal last, because refusal is a product state, not an error screen.

Warning

A medical assistant becomes dangerous fastest when it sounds confident after retrieval has already failed. Silence, uncertainty, and escalation must remain first-class outputs.

Stated Components

  • Trusted medical PDFs, guidelines, and PubMed-style references
  • PyMuPDF extraction, cleanup, chunking, embeddings
  • Qdrant indexing with reranking before generation
  • Constrained answers from retrieved context only
  • FastAPI interface with refusal behavior as a feature

Protocol 01

Risk Boundary

The strongest line in the project description is also the most important safety control: the assistant is designed as an education-focused system rather than a diagnosis engine. That sentence should not live in marketing copy alone. It has to shape what enters the system, what leaves the system, and which requests are declined before any answer drafting begins.

A medical evidence assistant should be treated as a constrained retrieval and synthesis surface over a limited corpus, not as a clinical thinker. The difference is practical. If a user asks for a summary of guideline recommendations, the system may be able to respond when evidence is retrieved, ranked, and cited. If the user asks whether their own symptoms indicate appendicitis, whether a dose should be changed, or whether a new lab result is safe to ignore, the safe design posture is no longer explanation. It is refusal or escalation. The assistant may still be useful in healthcare without crossing into medical decision authority, but only if the system boundary is narrow enough that operators can tell when it has been crossed.

The stated architecture supports that narrower posture. Trusted-source scope, retrieval before generation, and refusal behavior all suggest that the design is trying to prevent model free-association. Still, those mechanics are only effective if the product team treats them as binding rules rather than as guidelines that can be relaxed when recall looks low or users want more conversational answers. In high-stakes domains, permissive fallback behavior is often the real defect. The model is not unsafe because it can predict the next token. It becomes unsafe when the surrounding product invites it to do so after the evidence path has run dry.

Boundary Rule

If the system cannot anchor a response to retrieved, in-scope evidence, it should not switch to general model knowledge. The absence of support is itself a valid product outcome.

The boundary should also be explicit at the API level. FastAPI exposure is useful because it can enforce structured inputs and outputs instead of tolerating arbitrary prompt strings that smuggle clinical intent past the guardrails. A well-shaped request object can carry question text, requested task type, user role, and a safety route. That makes it easier to distinguish an evidence summary request from a personalized medical interpretation request before retrieval has even begun. It also makes audit review possible.

The boundary must cover language style as well as intent. An answer can be technically limited yet still sound like advice if it uses directive phrasing such as “you should take,” “this means you have,” or “it is safe to wait.” For an education-focused assistant, tone is not cosmetic. Tone is part of the control system. The safer pattern is explanatory language tied to source context: what the retrieved guideline says, what population it addresses, where evidence is uncertain, and why the assistant cannot apply that general statement to a specific person. That distinction protects against the common failure mode where a grounded answer remains factually sourced but is framed like clinical instruction.

{
  "task": "evidence_summary",
  "question": "What do current hypertension guidelines say about home BP monitoring?",
  "user_context": {
    "role": "general_public",
    "patient_specific": false,
    "urgent_symptoms_present": false
  },
  "routing_policy": "medical_evidence_only"
}

This minimal request shape is not interesting because it is complex. It is useful because it narrows interpretation. A route like medical_evidence_only makes the system intent visible: answer only within the evidence review lane, and do not perform personalized assessment even if the generation model could produce fluent text. That is the kind of constraint that matters more than a sophisticated prompt.

Finally, the risk boundary should distinguish between “can answer carefully” and “should answer at all.” General literature summaries, definitions of study terms, or comparative descriptions of published recommendations can be appropriate if retrieval succeeds. Symptom triage, medication dosing, interpretation of individual reports, and urgent situations should shift to refusal or direct escalation. This is not because those tasks are linguistically harder. It is because the harm of an incorrect or overconfident answer is qualitatively different. The architecture review only makes sense if that difference is honored up front.

Protocol 02

Source Selection And Retrieval

Once the boundary is defined, the next safety question is not “which model answers best?” It is “what is the model allowed to see, and how reliably can the system recover the right fragments from that corpus?” In this project, the README points to medical PDFs, guidelines, and PubMed-style references, plus PDF extraction, cleanup, chunking, embeddings, Qdrant indexing, and reranking. That is a reasonable safety-oriented retrieval spine if each stage is treated as a control point rather than a throughput step.

Source selection is the first control point. “Trusted sources” has to mean more than documents that look formal. A safe corpus needs repository-level discipline: guideline publisher, publication date, document version, document type, and whether the material is normative guidance, review literature, trial evidence, or background explanation. Without those distinctions, retrieval can surface a perfectly relevant-looking passage that is simply the wrong kind of authority for the question. For example, a narrative review may explain a topic clearly but should not silently outrank a current guideline when the user asks what is recommended in practice.

PDF extraction via PyMuPDF is another place where medical systems deserve extra skepticism. Clinical tables, footnotes, multi-column layouts, figure captions, and superscript references do not survive naive extraction cleanly. If the ingestion layer strips section titles, detaches recommendation strength qualifiers, or merges headers into paragraph text, the downstream embedding index will faithfully preserve the wrong unit. The architecture therefore depends on cleanup rules that preserve provenance fields and document structure well enough that a retrieved chunk still tells the answer layer what it is, where it came from, and how it should be interpreted.

Chunking has to balance semantic completeness against retrieval precision. Chunks that are too short lose recommendation context: the sentence with the action survives, but the qualifiers on population, contraindication, or evidence level do not. Chunks that are too long tend to over-bundle related ideas and make reranking less crisp. In medical evidence systems, the right chunk is rarely just “N tokens.” It is more often a structurally coherent excerpt bounded by headings, list items, recommendation bullets, or abstract sections, with metadata that makes later citation defensible.

Embeddings and Qdrant indexing are necessary infrastructure, but they are not enough by themselves. Dense retrieval is good at recovering semantically similar material; it is not inherently good at deciding whether the material is authoritative or specific enough for the question. That is why the README’s mention of reranking matters. In a medical setting, reranking should include metadata-aware preference for guideline material, population fit, and evidence freshness where the corpus contains multiple versions.

A good retrieval layer also has to preserve abstention. Teams often over-optimize for always returning something, because empty retrieval looks like failure in demos. Here, empty or weak retrieval is exactly the signal the later refusal layer needs. If the index is tuned to return vaguely related passages under all conditions, answer generation will inherit ambiguity and citation formatting will only make the result look more legitimate. Precision matters more than coverage once the product promises safety-aware medical answers.

{
  "source_policy": {
    "allow": ["guideline_pdf", "medical_pdf", "pubmed_reference"],
    "require_metadata": ["title", "year", "section", "source_type"],
    "prefer": ["guideline_pdf"],
    "reject_if_missing_text_quality": true
  }
}

This kind of manifest is useful because it turns “trusted source” into an operational rule. The safer retrieval architecture is boring in the right ways: explicit allowlists, version tracking, metadata preservation, and ranking logic that can explain why a chunk was surfaced. Medical question answering should be inspectable. If an operator cannot tell which document, section, and passage supported a sentence, the system may still feel polished, but it is no longer behaving like an evidence assistant.

The final point in retrieval is that ranking should be allowed to surface conflict rather than forcing an artificial consensus. Medical literature does not always agree, and guideline documents can diverge by jurisdiction or date. A well-designed evidence system should be able to retrieve that tension and pass it forward as structured uncertainty. Suppressing disagreement to produce a smoother answer is not a user benefit in this domain. It is a distortion. Retrieval is safe when it returns enough context for the answer layer to say either “here is the supported summary” or “the evidence base does not support a clean answer for this question.”

Protocol 03

Answer Assembly And Citation Behavior

The README says answer generation is constrained to retrieved context. That is the right intent, but in practice constraint has to survive the last mile of composition, where many otherwise careful systems loosen their standards and let a generation model fill gaps between snippets. This section matters because fluent language is where unsupported inference becomes hardest for users to notice.

The safest answer pattern is claim-by-claim assembly rather than general summarization. Each substantive statement should be traceable to one or more retrieved snippets, with citations attached at the point of use. That does not mean every sentence must be awkward or overburdened. It means the system should know, internally, whether a sentence is grounded, inferred from multiple grounded snippets, or unsupported. Only the first two categories belong in a user answer, and the second category should be narrow: synthesis is acceptable when the combination is explicit and faithful to the retrieved evidence, not when the model invents connective tissue that sounds plausible.

Citation behavior is therefore more than formatting. A numbered citation list at the bottom of a response is not enough if the mapping between claims and sources is loose. In medical contexts, the user must be able to tell which recommendation came from which kind of document, and whether the answer is quoting a guideline statement, summarizing several studies, or merely describing background context. A citation that points to a whole PDF after only one chunk was retrieved is not transparent. It gives the impression of broad support without showing the actual evidentiary path.

That is why evidence snippets should carry structured fields into generation: document title, section heading, year or version marker, and source type at minimum. The generation layer should not receive raw text alone. It should receive evidence objects. Once the model sees text without provenance, the temptation to produce elegant but ambiguous synthesis increases. Once it sees provenance objects, the system can ask the model to compose inside a frame that already knows where each claim came from.

Citation Discipline

A citation is not a decoration added after writing. It is a contract that the sentence would be materially weaker or absent if that supporting evidence were removed.

Another issue is overstatement. Even with trusted sources, the system should not silently convert a population-level statement into a patient-specific implication. A retrieved guideline may say that a certain intervention is recommended under specific conditions. The assistant can report that recommendation as published, with qualifiers intact. It should not translate that into “this applies to you,” because that step requires patient context and clinical judgment outside the stated boundary. Good answer assembly preserves the limits already present in the source material.

Uncertainty also belongs in the answer body, not only in a disclaimer footer. If the highest-ranked evidence is older, conflicting, indirect, or sparse, the answer should say so explicitly. Otherwise the system creates a confidence inversion: the weaker the evidence, the more users need a clean signal that the answer is conditional. Medical assistants often fail here by adding one generic caution at the end while presenting the main text in a decisive tone. That is not a minor stylistic flaw. It changes how users interpret risk.

def compose_answer(question, evidence):
    if not evidence or evidence.support_is_weak():
        return refuse("insufficient_evidence")

    return {
        "summary": build_grounded_summary(question, evidence),
        "citations": attach_claim_level_citations(evidence),
        "uncertainty": render_known_limits(evidence),
        "medical_boundary": "Not for diagnosis or personal treatment decisions."
    }

This sketch is intentionally plain. The important detail is that refusal remains available at composition time. Retrieval may have returned some text, but “some text exists” is not the same as “the answer is supportable.” The composition layer should still be able to decline, especially when the retrieved snippets are topically related but do not directly answer the question or when the evidence base is internally inconsistent.

The model named in the README, Gemini Flash, is not the main safety story here. Any generator that is fast and coherent can still over-compress or smooth over conflict. The relevant architectural question is whether the model is forced to operate inside a narrow answer schema with explicit citation and refusal channels.

The answer should also resist laundering citations through secondary explanation. For example, if a retrieved chunk says evidence is limited in a subgroup, the model should not write an expansive educational paragraph about that subgroup and then cite the limited passage as if it supported all of the added explanation. That common maneuver is especially tempting in medical writing because background knowledge sounds helpful. In this architecture, background knowledge that is not retrieved context should simply remain unused.

Finally, the assistant should prefer a shorter answer over a complete-looking one. In safety-sensitive domains, verbosity can create false comprehensiveness. A disciplined response that states the supported point, names the source type, notes the limits, and declines to extend beyond the evidence is often the correct product behavior. Users may sometimes want a longer answer; that does not mean the system should infer beyond what the evidence path can justify.

Protocol 04

Refusal And Escalation Cases

The README treats refusal behavior as a product feature. That is the right instinct and it deserves emphasis. In a medical evidence assistant, refusal is not what happens when the system is weak. Refusal is what demonstrates that the system understands its own role. A product that never refuses is usually not more capable. It is simply less honest about its operating boundary.

There are at least four refusal classes that should exist independently. The first is evidence insufficiency: no relevant chunks, low-quality extraction, stale material, or unresolved conflicts. The second is task mismatch: the user asks for a diagnosis, treatment recommendation, dose adjustment, or interpretation of personal data rather than an evidence summary. The third is acuity: the user mentions red-flag symptoms or urgent deterioration. The fourth is procedural ambiguity: the request is phrased in a way that looks educational on the surface but requires patient-specific inference once unpacked. Safe systems should not collapse all four classes into a generic “I cannot help with that” message, because each class suggests a different next step.

Urgency deserves particular discipline. If a question mentions possible emergency symptoms, the assistant should not hide behind a long explanation about evidence limitations. It should shift immediately to concise escalation language. In practical terms, that means brief direction to local emergency services or urgent clinical care rather than a mini-essay. High-risk scenarios are one place where less text is safer text. The goal is not to educate the user on the full decision tree at that moment. The goal is to stop the interaction from being mistaken for timely medical guidance.

For non-urgent but personalized requests, the refusal should explain the specific boundary. Saying “I am not able to answer that” is weaker than saying the assistant can summarize published evidence but cannot assess an individual’s symptoms, treatment plan, or medical records. Specific refusal language is not merely friendlier. It teaches users how the tool is meant to be used, which improves future request quality and lowers pressure on the generation layer to improvise.

Low-support refusal is different again. Here the tool should indicate that it could not retrieve enough reliable evidence from its approved sources to answer responsibly. That message protects against a dangerous user assumption: that the absence of an answer means the topic has no evidence. More often, it means the system’s source set, extraction quality, or ranking outcome did not justify a response. The refusal should therefore remain epistemically precise. It is the system declining to answer, not the system declaring the literature empty.

def refusal_route(request, evidence):
    if request.user_context.get("urgent_symptoms_present"):
        return "escalate_urgent_care"
    if request.user_context.get("patient_specific"):
        return "refuse_personalized_medical_advice"
    if not evidence or evidence.support_is_weak():
        return "refuse_insufficient_evidence"
    return "answer_with_citations"

The important architectural point is that refusal routing can occur both before and after retrieval. Some questions should be declined on intent alone. Others only become clear after the evidence layer returns weak or conflicting support. Systems that put refusal only at the front gate miss the latter class; systems that put refusal only at the end waste time retrieving for questions that should never have entered the answer path. The safest design uses both checkpoints.

One final concern is pressure from user persistence. Medical assistants are often probed with repeated rephrasing after a refusal. The model should not interpret repeated pressure as a reason to offer partial advice. If anything, repeated attempts after a boundary decision are a reason to keep the output shorter and more consistent. Safety policies that degrade under conversational persistence are not policies. They are suggestions the model may ignore when nudged hard enough.

The practical test for this architecture is simple: when evidence is weak or the request is unsafe, does the product remain helpful without becoming permissive? Helpfulness here means clear explanation, source-conscious limits, and actionable escalation where appropriate. It does not mean stretching the answer until the user feels satisfied. In medical systems, refusal quality is part of answer quality.

Operational Close

Release Conditions

The architecture described in the project README is directionally sound for a narrow medical evidence assistant, but only if the product remains strict about what counts as support and what counts as a refusal case. The safest interpretation of this design is not “medical AI that answers carefully.” It is “a scoped evidence interface that sometimes answers and often declines for good reasons.”

  • Keep the mandate narrow: evidence summary and citation, not diagnosis, dosing, or patient-specific interpretation.
  • Treat source selection as a governance layer: document type, version, date, and provenance should survive ingestion into the index.
  • Require claim-level grounding during answer assembly so citations explain why a sentence exists, not just where the page came from.
  • Preserve refusal as a primary output, with separate paths for urgent escalation, personalized care requests, and insufficient evidence.
  • Audit the FastAPI contract for structured routing fields so unsafe intent is caught before and after retrieval, not after free-form text generation.

If those conditions hold, the assistant can occupy a useful and defensible role: a controlled gateway into approved medical literature, with explicit boundaries and visible limits. If those conditions slip, the same interface will still sound polished, but it will stop behaving like a safety-aware evidence system.
